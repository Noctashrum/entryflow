  > 作为产品负责人，请用多 agent Vibe Coding 构建 EntryFlow（竞途有序）。目标是让准备参赛的学生和团队把赛规、项目摘要与核验结果转成可追踪的投递任务。用户先录入赛规和项目摘要，随后对照原文确认门槛，最后生成清单、更新负责人和进度并导出。将界面、规则证据和工作流划给不同 agent 编写代码，保留各轮实际提示、反馈、修正和验证。每个提交对应已落地的模块或迭代。

## 2026-11-16 · 集成验收

- 浏览器使用官方赛规摘编和虚构项目跑通全流程。识别 7 项门槛、6 项独立提交材料。初次解析漏识别的组别、仓库、Git 历史和技术文档已回归验证，低置信度的项目线索留空。
- 将一项门槛设为符合并写入核验备注。搜索「演示视频」命中第 11 行原文。生成清单，完成 README 复现指南并填写负责人。刷新后状态与负责人仍在。浏览器下载的 Markdown 保留赛规引用、核验备注、负责人及复选框状态。
- 修改摘要后，投递清单明确显示资料已变更。再次提取后门槛回到待确认，重新生成仍保留来源匹配的 README 任务状态。390px 宽度下无页面横向溢出，进度和导出已排在任务列表之前。
- 用两行文本的测试 PDF 经浏览器文件选择器导入，实际读取文字层并写回赛规字段。规则、清单与项目摘要保存在本机浏览器。可选 RAG 通过模拟模型服务验证命中上下文和引用检查，商业模型的真实连接留待填写服务端配置后验证。

## 2026-11-16 · 投递复核迭代

编排 agent 将检索与模型服务、浏览器工作流分别交给独立 agent。两者共用证据格式，通过带出处的任务衔接。开发提示、接口反馈、修正与回归分别记在[检索与模型服务](agent-rag-engine.md)和[投递复核交互](agent-rag-workflow.md)。

- 浏览器用官方摘编和虚构项目完成三个预设复核及自定义提问。仓库建议只采纳一次，刷新后保留任务进度，导出的 Markdown 同时包含原问题、赛规原文及项目摘要出处。
- 通过真实应用服务对接模拟模型，在浏览器手动发起模型复核、检查双来源引用并把建议加入清单。使用的是虚构项目和模拟上游。对外部实际模型的调用需要配置服务。
- 390px 视口无页面横向溢出。切换问题会提示运行当前问题，修改资料才提示资料变更。工作流回归覆盖旧摘要行号失效、重复采纳和引用导出。
